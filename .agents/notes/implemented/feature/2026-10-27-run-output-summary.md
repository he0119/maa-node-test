# Agent Note: 测试输出末尾补一块「结果」

Status: implemented

## Problem

测试输出面板里原本是两类内容直接堆在一起：runner 的原始 stdout（MaaFW 准备、资源加载、每组每张图的判定，几十到上百行），加上扩展在每个「通过但带明细」的文件节点上各追加一段 `· 标题 / · 明细`。

跑一个文件还好，点目录节点跑十几个文件之后：末尾是几十行「✓ 文件 …」和逐条缺图说明，真正要看的「哪条用例没通过」埋在中间；反过来想知道「一共跑了多少条、通过多少」得自己数。用户的原话是「这段看起来好难受」。

原始日志不能删：跑不起来的时候（MaaFW 下载失败、资源打包报错、node 版本不够）唯一的信息来源就是它。

## Decision

1. `src/core/runSummary.ts` 新增纯函数 `buildRunSummary()`：输入「每个文件的结论 + 用例总数 + 有问题的那几条用例 + 耗时」，输出一段固定形状的文本块 —— 结论一行、文件计数、用例计数、耗时，空行之后按「失败 → 没跑起来 → 缺图跳过」分段，每条用例一行（`文件 · 第几条 · 短标题`）。通过的不列。
2. `src/testing.ts` 里原始 stdout 前面加一条分隔线（`RAW_LOG_BANNER`，写明「排错看这里」），跑完在锚点节点上追加结果块。批量跑和单跑一条用例用同一套形状，用户不用记两套读法。
3. 删掉原来「每个通过节点各追加一段明细」的逻辑（`applyMark` 的 pass 分支）：那正是把输出刷成流水账的来源，「哪几条因缺图跳过」由结果块统一列。
4. 结论的措辞分四种，不肯把「没验证」说成「通过」：
    - 全部通过 → `结论：通过`；
    - 通过但有缺图跳过 → `结论：通过（其中 N 条用例缺图跳过，没有真正验证到）`；
    - 有通过之外的用例但一条都没真跑（例如单跑一条缺图用例）→ `结论：没有验证到（N 条用例缺图跳过，不算失败）`；
    - 有失败 / 没跑起来 → `结论：没通过 —— X 个文件失败、Y 个文件没跑起来`；
    - 取消 → `结论：已取消（运行被中断，结果不完整）`，并且**不给计数**（跑了一半的数字比没有数字更误导）。

## Alternatives considered

**过滤原始日志，只留结论行。** 看着最干净，但把排错能力一起删了：进程没起来、MaaFW 下载失败、某个组一个用例都没匹配到，这些只有原始日志里才有。改用「原样保留 + 末尾补摘要」。

**把摘要放开头。** 测试输出面板跟着输出滚动，跑完时视线停在末尾；放开头等于每次都要往上翻。原始日志前面那条分隔线已经提示了「后面还不是结论」。

**只靠节点消息，不写输出。** 失败/跳过节点的消息本来就有原因，但 `TestRun.passed()` 不接受消息，通过文件的缺图说明没地方放；而且「一共跑了多少条」这种统计哪都装不下。

**用 ANSI 颜色/粗体高亮结论。** 测试输出面板对 ANSI 的处理随版本变，纯文本分隔符（`━━━━`）在任何版本都一样能看清。

## Consequences

- 跑完一眼能看到「通过没通过、几个文件、几条用例、耗时」，出问题的用例逐条列在下面；
- 代价是计数里「用例总数」来自面板节点数（文件下的子节点个数），不是 runner 报的数字 —— runner 只报有问题的用例，通过的不报，所以只能这么数；
- 结果块是纯文本，没有任何颜色或折叠；
- 结果块挂在本次运行的锚点节点上：批量跑时是第一个目标，其它目标节点只显示自己的标记（通过/失败/跳过），不会有各自的摘要。
