# Agent Note: 插件独立成仓，调试窗口打开被测仓库

Status: implemented

## Problem

扩展有自己的 TypeScript 构建、依赖和发布流程，不应让被测仓库承担这些产物。另一方面，扩展运行时需要读取被测仓库的配置与资源；只打开插件源码目录，会把工作区选错。

## Decision

- 插件独立构建与发布，被测仓库只需要安装它自己使用的 maa-tools 并定义测试，不需要把扩展源码加入其构建。
- 运行插件的调试窗口打开**被测仓库**。仓库自带的多根工作区和 launch 配置目前以相邻的 MaaEnd 为例，换仓库须改这些路径，并非产品只支持 MaaEnd。
- 保留三种调试入口：多根工作区、只开插件目录后传入被测目录、在被测仓库窗口加本机调试配置。具体操作见 [README](../../../../README.md#开发态)。
- 扩展通过被测仓库的 `node_modules/@nekosu/maa-tools/bin/maa-tools` 调用收集与运行。不会通过其他目录的包名解析寻找替代版本。
- `configPath` 用于选择工作区根，并传给收集和运行；`testsetDir` 只影响编辑辅助，不覆盖框架运行配置。

## Alternatives considered

**放进 MaaEnd 的开发目录或 pnpm 工作区。** 会把扩展依赖、构建和格式检查加到被测仓库，独立发布也更麻烦。扩展不只服务一个仓库，单独维护更明确。

**扩展自己附带 maa-tools。** 容易与被测仓库命令行使用不同版本。调用仓库的版本可以减少这类差异，同时不多安装一套框架依赖。

**自动向工作区外寻找配置。** 多根工作区和软链接场景容易选中用户没有打开的仓库。现有规则是优先选择包含 `configPath` 的工作区文件夹，否则选第一个；无法运行时明确指出配置问题。

**只支持一种调试入口。** 多根工作区适合同屏编辑扩展和测试文件，单目录入口适合已有工作流；三种入口最终都把正确目录交给调试窗口，不需增加运行规则。

## Consequences

- 扩展源码改动不会成为被测仓库的提交；运行识别仍可能由 maa-tools 在其配置的日志目录写文件，不能承诺运行后仓库没有新增产物。
- 被测仓库依赖没装好或接口不支持时，扩展明确报错，不换用另一份工具。
- 默认调试路径只适用于当前示例布局；README 要让用户知道哪里需要修改。
- 格式工具可复用本机 MaaEnd 安装的版本，但它是开发环境选择，不是插件运行依赖。工作区文件保持纯 JSON。
